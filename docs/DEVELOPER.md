# Developer manual — `deauth_guard`

## Purpose

`deauth_guard` is a **Home Assistant custom integration** that surfaces **802.11 deauthentication-related detections** (and, in later stages, related management frames) to Home Assistant as **events**, **services**, and **entities**, with a **bounded local history** for dashboards and automations.

This document targets contributors and advanced users who self-manage Home Assistant Core on Linux (including Raspberry Pi 3B).

## Runtime model

1. **Config entry** (via UI) sets **`radios`**: a list of up to three `{ "interface", "channels" }` objects (Radio 1 = simulation or a system interface; optional Radio 2/3 for extra hardware), plus **shared** **alert rules** (up to two sliding-window rules in the form), `history_max_entries`, and `simulation_interval_seconds`. See **[User manual — Configuration storage (JSON reference)](USER.md#configuration-storage-json-reference)** for example payloads.
2. A **`DataUpdateCoordinator`** receives capture callbacks. **Channel filter** runs first (not applied in simulation: synthetic events use random channels for testing). **Alert policy** decides whether to fire a bus event; **every** filtered event is still appended to **`DeauthHistoryStore`** and updates the `last` sensor, but `deauth_guard_attack` is emitted only when the alert condition matches.
3. For **no alert rules** and a **non-simulation** interface, only the **first** post-filter detection after (re)load raises `deauth_guard_attack` (automation “first seen”). With **simulation** and no rules, every tick can emit (and default interval is 10s).
4. Real monitor-mode packet capture will require **elevated privileges** when a non-simulation path is implemented; see `docs/DECISIONS.md`.

## Event contract (automation API)

Fired on the event bus (topic for stable filtering):

- **`deauth_guard_attack`**

Typical `event_data` keys (all optional if unknown). **`band`** values in simulation follow `const.BAND_*` (e.g. **`2.4 GHz`**, **`5 GHz`**, **`6 GHz`**)—human-readable labels, not snake_case slugs.

| Key | Type | Description |
|-----|------|-------------|
| `source` | `str` | Normalized MAC, upper-case hex with colons |
| `destination` | `str` | Same as above |
| `bssid` | `str` \| `None` | If inferable from frame / context |
| `reason` | `int` \| `None` | 802.11 *Reason Code* when available |
| `rssi` | `int` \| `None` | dBm, if available |
| `interface` | `str` | Logical interface name (e.g. `wlan0`, `sim0` in simulation) |
| `channel` | `int` \| `None` | Primary 802.11 **channel number** (1–13 on 2.4 GHz, etc.) when available |
| `band` | `str` \| `None` | Coarse band label (simulation: see `BAND_2_4_GHZ` / `BAND_5_GHZ` / `BAND_6_GHZ` in `const.py`) |
| `wifi_phy` | `str` \| `None` | Optional short PHY / generation label when known, e.g. `b`, `g`, `n`, `a`, `ac`, `ax`, `be` (not every capture path can fill this) |
| `simulation` | `bool` | `true` if generated by the simulator (must not appear as real traffic) |
| `emit` | `str` | Present on emitted events (e.g. `alert`); use to distinguish from historical-only rows in services |

`deauth_guard_attack` is only fired when the **alert policy** allows it (not on every stored row). Use **`deauth_guard.get_history`** for the full post-filter list.

### Edge cases (UI / capture)

- **Empty channel list** = listen to **all** reported channels. Non-empty = drop frames whose `channel` is known and not in the set; **unknown** channel: **keep** (and log at debug) so we do not hide activity when metadata is missing.
- **Restricting channels** (hardware) usually **reduces** work when using channel hopping; software-only filtering after a wide capture does not save RF work but keeps automations focused.
- **Simulation** ignores the channel allow-list and uses a **random** channel every tick (default **10s**) so the UI can be tested against diverse channels without matching the user’s selection.

Automations should filter on `event_type` and optionally on `data.simulation` in development.

## Services

Registered from `services.yaml` (see in-tree file). The integration registers handlers in `__init__.py` after setup. Handlers are **async**; any blocking work must be delegated to an executor.

## Local storage

`DeauthHistoryStore` uses `homeassistant.helpers.storage` with a versioned store key under the Home Assistant config directory. History is **bounded** by `history_max_entries` to limit flash wear and memory on small boards.

## HACS / install

Root **`hacs.json`** and **`custom_components/deauth_guard/brand/`** satisfy the HACS action. Add the repo in HACS as a **custom repository** (or publish to the [default store](https://hacs.xyz/docs/publish/include) after meeting listing requirements). Manual install: copy `custom_components/deauth_guard` into the HA configuration `custom_components` directory, restart, add integration from UI.

## Development workflow

1. Use a throwaway **Home Assistant Core** dev venv (see official dev setup) or a test container.
2. Enable **simulation mode** in the integration so no WiFi stack is required.
3. **Lint** (if configured): `ruff check custom_components/deauth_guard` from the repo root.

### Running hassfest locally with Docker

This matches what **`home-assistant/actions/hassfest`** runs (see [action.yml](https://github.com/home-assistant/actions/blob/master/hassfest/action.yml)): mount the **repository root** at **`/github/workspace`** and use the official image.

From the clone root (where `custom_components/` and `hacs.json` live):

```bash
docker pull ghcr.io/home-assistant/hassfest
docker run --rm -v "$(pwd):/github/workspace" ghcr.io/home-assistant/hassfest
```

The container discovers every `manifest.json` under the workspace and runs `script.hassfest --action validate`. Fix any printed errors before opening a PR.

**HACS validation** does not use this image; it is what **`hacs/action`** runs on GitHub. To reproduce elsewhere without Cursor: push a branch and check the **Validate** workflow, or use a machine with Docker only for the command above (hassfest) and rely on CI for HACS.

## Tests

The repository includes **`pytest`** suites under `tests/`. You do **not** need the full `homeassistant` package on your machine: `tests/ha_stubs.py` registers enough of `homeassistant.*` to import the integration package (`const`, `core` + `ServiceCall` / `SupportsResponse`, `config_entries`, `helpers.config_validation`, `helpers.update_coordinator` / `DataUpdateCoordinator`, `helpers.event`, `helpers.storage`, etc.) plus **`voluptuous`** from **`requirements-dev.txt`**. The shim set grows when imports in `__init__.py` change—keep it aligned or tests will fail on `ModuleNotFoundError`.

```text
python -m pip install -r requirements-dev.txt
python -m pytest tests/ -v
```

Coverage (optional): `python -m pytest tests/ --cov=custom_components/deauth_guard --cov-report=term-missing`

| Test module | What it covers |
|-------------|----------------|
| `test_history.py` | `DeauthRecord`, `DeauthHistoryStore` (ring buffer, persist via mocked `Store`; `max_entries` respects `LOWEST_HISTORY_MAX`) |
| `test_rf_synthetic.py` | `synthetic_channel_band_phy()` (channel / band / `wifi_phy` ranges) |
| `test_last_event_text.py` | `last_event_summary()` (same string as the last-event sensor) |

To exercise the real `homeassistant` package (e.g. future integration tests), install it in the same environment: `pip install "homeassistant>=2024.5.0"` (Python 3.12+).

## Raspberry Pi 3B

- **ARMv7**, limited RAM: keep default `history_max_entries` conservative; avoid large Python allocations in the hot path.
- Prefer a **dedicated 802.11 adapter** with known Linux monitor-mode support; onboard WiFi may be less flexible depending on the driver and regulatory behavior.
